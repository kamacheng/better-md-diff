# 个人版：变更审阅与版本对比需求

- **状态**：核心需求已经用户确认；本文中的“技术默认建议”尚属设计，不等于新增需求已经确认，也不表示功能已实现。
- **开发分支**：`personal/review-workflow`，从 `main` 的 `208f410`（0.3.0）创建。
- **使用范围**：本文定义个人桌面端审阅方案，完整工作流尚未接入。个人分支与界面改进已按授权合并至 `main`；用户进一步授权已启用的 HEAD 对比界面改进随 0.4.0 社区版发布（含标签与 release）。这不表示本文的完整审阅/GitLab 功能已经开放。
- **术语**：[CONTEXT.md](../CONTEXT.md)。实施顺序见[开发计划](personal-review-plan.md)。

## 1. 用户场景与目标

用户在 Obsidian 中手工写作，并让外部 AI 直接修改文件。任务可能涉及整个 vault 中事先未确定的文档。既有从空白创作，也有对现有稿件的修订；用户可能边审阅边手工改写。

本地 vault 由用户的个人 GitHub 仓库管理，与公司的 GitLab 仓库没有关联。文档另行上传到公司自建、私有的 GitLab 项目；公司文件与本地文件不要求有相同路径或共同 Git 历史。

要解决的问题：

1. 认可但未提交的改动不应一直混在待审改动里。
2. 拒绝不满意的修改，不应误伤此前已经认可的内容。
3. 不要求每次让 AI 修改前，先操作插件保存快照。
4. 可以另外查看相对本地 HEAD 或公司 GitLab 指定文件版本的差异。

## 2. 已确认的功能范围

### R01 — 两个 Tab，共用差异展示

插件面板提供 **变更审阅** 和 **版本对比** 两个 Tab。

| Tab | 对照内容 | 核心能力 |
| --- | --- | --- |
| 变更审阅 | 当前文档的认可内容 | 接受此项、拒绝此项、接受本文全部改动、撤销认可 |
| 版本对比 | 用户选择的参考版本 | 读取参考内容并展示与当前文档的差异 |

两种模式共用差异计算、字词高亮、复制和定位能力，但状态独立。切换 Tab、切换参考来源或刷新 GitLab 内容，都不能修改认可内容。

接受后的文字仍可能相对 HEAD 或 GitLab 有差异；这不是错误，也不代表接受失效。

### R02 — 跟踪整个 vault，界面只显示当前文档

- 跟踪整个 vault 中的 Markdown，包括未打开的文档。
- 界面只显示当前打开的 Markdown 文档，不增加待审文档列表。
- 不依据修改来源自动认可；手工和 AI 修改执行同一套规则。
- 不识别或猜测 AI 任务轮次。
- 没有可用的本地 Git、文件未被 Git 跟踪或者公司 GitLab 不可访问，都不能阻止独立的变更审阅。

### R03 — 仅首次启用初始化现有文档

首次启用个人版审阅、尚无认可记录时，把当时已有 Markdown 文档的内容初始化为已认可。首次采用此规则意味着这些现有修改不会再作为待审。

后续启动、重新启用插件、重新打开文件或者新一轮 AI 修改，都不重新认可全文；继续使用已保存的认可内容。

“首次启用”针对这个 vault 的审阅记录，不是每一次 `onload`，也不是该文件第一次被打开。损坏或读不到的记录不能被当成“从未初始化”。

### R04 — 初始化之后新增文档全篇待审

首次初始化完成后新增的 Markdown，无论手工创建、AI 生成还是复制进入 vault，认可内容初始为空白。

包括插件关闭期间新增的文件：重启后也不能把其正文自动认可。用户可以逐项接受，或使用“接受本文全部改动”。

### R05 — 逐项接受

- 正文不变，只把目标改动项纳入该文档的认可内容。
- 其他待审改动不被连带接受；显示上下文也不属于接受范围。
- 以后再修改已经接受过的内容，新的差异重新进入待审。
- 不暂存、不提交，也不改变任何参考版本。

例：认可内容为 `A1 / B1`，正文变为 `A2 / B2`。只接受第一项后，认可内容为 `A2 / B1`，正文仍为 `A2 / B2`。这里 A、B 表示由未变化正文隔开的两个独立改动项；若增删连续，仍按一项操作，不能假定能任意拆开。

### R06 — 逐项拒绝

- 仅将目标改动项恢复为对应的认可内容；认可内容本身不变。
- 恢复目标不是上次保存、上轮 AI 修改或者当前所选 GitLab 版本。
- 继续保留现有还原操作的预览确认、取消、过期检查和单次编辑器可撤销事务。

例：`7天` 已认可，随后先改为未认可的 `10天`，再改为未认可的 `14天`。拒绝这一项恢复 `7天`，本版不负责恢复 `10天`。

新文档没有认可过的正文。拒绝新增内容会撤掉对应文字，不会恢复未认可的手写初稿；操作不删除文件本身。

### R07 — 接受本文全部改动

- 仅作用于当前文档，将本次操作核对的正文内容整体设为认可内容。
- 包含该篇的手工和 AI 待审修改，不自动区分来源。
- 不影响其他文档，不提供跨文档或全 vault 的批量接受。
- 后续新修改仍待审，不得把操作期间后来写入的内容顺带认可。

常用流程：先拒绝不满意的部分，再接受本文剩余改动。

### R08 — 撤销认可

对“接受此项”和“接受本文全部改动”提供撤销认可能力。撤销时恢复操作前的认可状态，正文不回退；根据当前正文重新计算待审差异。

它不等同于编辑器的 Ctrl/Cmd+Z。后者用于撤销拒绝操作对正文的修改。撤销深度与保留方式见技术默认建议 D01。

### R09 — 重启与关闭期间的变化

- 认可记录需要持久化，重启后仍能区分认可内容与待审变化。
- Obsidian 关闭期间的多次修改，仅要求重新打开后能审阅累计变化。
- 不要求捕获关闭期间的中间稿，也不要求恢复从未认可的历史版本。
- 这一能力以设备仍保有该 vault 的记录为前提；多设备认可状态同步不是本次目标。
- 如果所有认可数据及初始化标志都被外部清除，仅凭正文无法证明此前是否初始化过，更无法恢复认可内容。这属于记录丢失后的恢复/重新初始化，不保证无损；可检测的缺失或损坏必须报错，不能自动通过待审。

### R10 — 本地 HEAD 对比

保留当前文档与本地 Git HEAD 的对比能力。本地 HEAD 属于个人 GitHub 工作目录，不代表公司 GitLab 的最新版本或已交付版本。

本版不新增本地历史提交浏览器、Git 写操作或仓库同步功能。

### R11 — 公司 GitLab 文件链接对比

- 支持公司自建私有 GitLab 的仓库 Markdown 文件页链接，典型形式为 `https://gitlab.example.com/group/project/-/blob/main/docs/note.md`。
- 明确选取当前本地文档，粘贴远端对应文件链接，配置读取凭证后读取原文并比较。
- 可记住本地文档与远端文件链接的对应关系；不能从个人仓库的 remote 自动推断公司项目。
- 显示参考来源、引用名称及本次实际读取的提交标识。
- 分支链接对应的内容可能变化；本次读取结果保持固定，显式刷新后再切换到新结果。
- 只从公司 GitLab 读取参考内容，在本机比较；不上传本地正文，不克隆整个公司仓库，不提交或推送。
- GitLab 读取失败不能改变认可内容或本地正文。

链接中的引用可能是分支、标签或提交。这是读取既定链接的能力，不等于需要新增历史选择器。

### R12 — 数据与凭证隔离

- 凭证、远端正文缓存不得默认放进可能提交或同步到个人 GitHub 的文件中。
- 不把令牌放进链接、错误提示、日志、测试夹具或文档。
- GitLab 网络访问必须源自用户配置的实例与对照链接，而不是自动扫描并连接本地 Git remote。
- 远端 Markdown 作为文本展示，不执行其中的 HTML、脚本或自动加载外部资源。

## 3. 不在本次范围

- 任意两个本地文件的对比、GitLab Wiki、MR 文件选择器。
- 本地历史提交浏览器、未认可中间稿时间线、AI 任务轮次识别或 AI 工具集成。
- 待审文档列表、跨文档批量接受、全部拒绝按钮。
- 按单字或任意选区拆分一个连续改动项；保持现有连续改动项粒度。
- 自动上传、暂存、提交、推送，或把“接受”映射成 Git 操作。
- 多设备同步认可记录、文件回收站、自动恢复已经删除的整个文件。
- 社区发布、公开 release、生产 vault 自动安装覆盖。

## 4. 技术默认建议（与用户已确认需求区分）

这些是控制范围和保护内容的建议；实施发现不可行时应说明，不得默默降低保护。

| ID | 建议默认 | 原因与限制 |
| --- | --- | --- |
| D01 | 每篇文档保留最近一次成功接受的撤销记录，并随认可内容持久化；不提供多步认可历史或重做 | 满足误接受恢复；以后再接受会替换该篇的撤销目标，执行撤销后清除该目标。撤销不覆盖后来编辑的正文 |
| D02 | 认可记录、撤销记录、远端链接映射保存在设备本地的 vault 外；远端正文先仅缓存于内存 | 避免通过个人 GitHub 意外带出旧正文、公司链接或缓存。需验证真实存储位置与隔离能力 |
| D03 | 优先使用宿主的凭证存储；不支持时只保留本次会话的令牌，不回退到普通 `data.json` | 保持旧版兼容前提下不牺牲凭证隔离；实际持久化安全性需要宿主验证 |
| D04 | 默认打开变更审阅；编辑器差异标记跟随当前 Tab 的对照来源，明确标识来源且不叠加两套标记 | 避免面板显示 GitLab 差异、编辑器却无提示地显示另一套差异 |
| D05 | 保留现有 HEAD 逐项还原，明确标为“从 HEAD 还原”；GitLab 本版仅查看、定位与复制 | 不削减已有能力，也不把新增远端读取扩大成远端内容写入本地的功能。HEAD 还原后仍需按认可内容重新判断待审 |
| D06 | 能确认的在线文件/目录重命名迁移记录；未能识别的离线移动不猜测认可关系 | 离线未知路径按新文件待审；旧记录保留，正文不自动恢复或删除 |
| D07 | 初始化、存储、大小限制、网络错误明确显示为不可用或待处理，不假装“无差异”或“已认可” | 失败不能触发自动清空、重新初始化、使用错误版本接受或越界还原 |
| D08 | 初始化显示进度；读取中发生变化的文件不悄悄认可后来内容，暂停该文件初始化并提示核对 | 全 vault 读取不是瞬时原子快照，不能承诺启动同一毫秒捕获所有文件 |

## 5. 验收场景

以下均为**计划验收项，尚未针对新功能执行**。自动化需测试真实操作入口；涉及宿主同步、凭证和网络行为的场景，还需隔离 vault 实测。

| 编号 | 前置与操作 | 预期结果 | 对应规则 |
| --- | --- | --- | --- |
| A01 | 首次启用，vault 已有多篇文档，其中部分未提交 Git | 现有正文成为认可起点，没有待审；不修改正文或 Git | R03 |
| A02 | 首次初始化后新建、复制或由 AI 写入 Markdown | 正文相对空白全篇待审，不因第一次打开而被认可 | R04 |
| A03 | 初始化后关闭 Obsidian，修改旧文件并新增文件，再打开 | 旧文件相对已保存认可内容显示累计差异；新文件全篇待审 | R04、R09 |
| A04 | 已有待审修改，重启/禁用后重新启用插件/关闭文件再打开 | 待审仍存在，不重新认可全文 | R02、R03、R09 |
| A05 | 修改从未打开过、但已经初始化的文档，然后打开它 | 显示相对其认可内容的差异；不需要先打开才开始跟踪 | R02 |
| A06 | 手工修改与 AI 修改同一篇正文 | 都待审，不依据来源自动认可 | R02、R05 |
| A07 | `A1 / B1` 改为 `A2 / B2`，仅接受 A | 正文为 `A2 / B2`，认可内容为 `A2 / B1`，B 仍待审 | R05 |
| A08 | 在 A07 之后拒绝 B，再在编辑器撤销拒绝 | 拒绝后正文 `A2 / B1`；一次编辑器撤销回到 `A2 / B2`；认可内容不变 | R06 |
| A09 | 对独立插入、纯删除、连续替换分别逐项接受和拒绝 | 只改变目标项或其认可部分；上下文及其他项不受影响，含首尾行与末尾换行 | R05、R06 |
| A10 | 已认可 7天，未认可地先改为 10天再改为 14天，拒绝 | 恢复 7天；不会出现“恢复 10天”的历史承诺 | R06、R09 |
| A11 | 接受过某一项后，手工或 AI 再次修改同一处 | 新差异重新待审，不能通过隐藏标记掩盖 | R05 |
| A12 | A、B 两篇有待审，在 A 执行接受本文全部 | 仅 A 的认可内容更新；B 保持待审 | R07 |
| A13 | 分别误接受一项/整篇，再撤销认可；其间可继续编辑正文 | 认可内容恢复到该操作前，正文完全不回退，重新计算待审 | R08、D01 |
| A14 | 最近一次接受后重启，再撤销认可 | 最近一次撤销目标仍在；不影响其他文档 | D01 |
| A15 | 拒绝全新且没有认可正文的文档中的全部新增内容 | 对应正文变为空白，文件本身仍存在 | R04、R06 |
| A16 | 在审阅中接受，切换到 HEAD/GitLab 对比 | 认可记录保持；仍显示相对参考版本存在的差异；切回不再提示已接受内容 | R01、R05 |
| A17 | 使用个人仓库 HEAD 对比，然后从 HEAD 还原一项 | 保留原有预览与撤销；不改变认可内容，根据还原后正文重算待审 | R10、D05 |
| A18 | Git 不可用或文件尚未 `git add` | HEAD 对比报相应错误，但变更审阅可正常工作 | R02、R10 |
| A19 | 为本地文件指定不同项目路径的合法 GitLab 文件链接并读取 | 获取指定远端文本，显示实际引用和提交；本地路径无需与远端一致 | R11 |
| A20 | 保存文件对应链接后切换文件，再切回或重启 | 每篇使用自己的链接；不泄漏到其他文件，不自动触发非用户发起的远端加载 | R11、D02 |
| A21 | 已读取分支版本，远端分支更新，先不刷新再显式刷新 | 不刷新时参考内容固定；刷新成功后才更新标识和差异，认可内容不变 | R11 |
| A22 | 读取期间切换文件、Tab、链接或发起更新请求 | 旧响应不能覆盖新文档、新来源或较新的结果 | R01、R11 |
| A23 | 认证失败、404、网络错误、超限或非文本响应 | 明确失败，不把错误页当 Markdown，不修改正文或认可记录，不显示读取成功 | R11、R12、D07 |
| A24 | 检查所有持久化文件、请求、错误与日志 | 本地正文不上传；凭证不进入 URL/日志/个人仓库；请求不向非授权实例携带凭证 | R12、D02、D03 |
| A25 | 操作预览后正文/认可内容/模式变更，或者取消确认 | 过期/取消操作不执行；接受全部不能顺带接受新的正文版本 | R05、R06、R07 |
| A26 | 初始化或接受保存时磁盘失败、中断、数据损坏 | 不报成功，不重置成当前稿已认可；保留可恢复记录并明确提示 | R03、R09、D07、D08 |
| A27 | 在线重命名文件或目录；离线移动或删除文件后启动 | 已确认重命名迁移记录；无法确认身份时不猜测认可，不自动重建已删除文件 | D06 |
| A28 | 新版仍使用原来的复制、导航、中文/英文界面、源码/实时预览 | 保持现有行为；两个 Tab 可键盘操作，按钮和空态明确对照来源 | R01、D04 |

## 6. 技术验证与交付限制

- 保存全 vault 的认可内容不等于保存全 vault 的完整修改历史；只存功能所需数据。
- “跟踪整个 vault”不要求每次打开或定时轮询都为所有文件运行 Git、访问 GitLab或计算完整 diff。
- 本版保留现有文档大小/行数限制；超限文档明确报告，不默默跳过并标记认可。
- 未通过宿主实测前，不能宣称凭证存储加密、跨域重定向安全、跨进程写入原子性或真实公司 GitLab 已联通。
- 验收先用隔离 vault 和虚构文档，不对用户实际 vault 运行破坏性场景。连接真实公司 GitLab仅在用户配置并授权的环境进行；不索取聊天中的令牌。
- 不因个人版而删除现有安全检查、测试、国际化或社区发布工作流。完整审阅开发不触发发布；另获授权的 0.4.0 仅发布已启用的 HEAD 对比功能，并沿用现有签名发布工作流。
